Test audit: Northwind Bookings

2-week audit · Web app and REST API · Fictional example

1. Summary

Northwind ships every two weeks, but each release waits on a three-hour regression run that fails for reasons unrelated to the change about one run in seven. The team has stopped trusting red builds. Most of the risk sits in payments and booking changes, which have the least automated coverage.

3. Top findings

Shared test accounts cause most flaky failures High

Evidence:
31 of the 44 failures in the last 30 runs came from tests editing the same staging accounts at the same time.
Impact:
Real regressions are hidden among false alarms, so red builds get re-run instead of read.
Recommendation:
Create a fresh account per test through the API and delete it afterwards.

Payments have no automated checks below the UI High

Evidence:
Refunds, partial payments and currency rules are only covered by two slow UI tests.
Impact:
The area with the highest cost of failure gets the least feedback.
Recommendation:
Add API tests for each payment rule first, including error and negative paths.

Fixed sleeps instead of waiting for the page High

Evidence:
212 hard-coded sleeps across the UI suite, adding about 40 minutes to every run.
Impact:
Slow runs, plus failures whenever staging is slower than the sleep.
Recommendation:
Wait on page state; Playwright's built-in waiting removes most of these during the move.

Nothing runs before code merges Medium

Evidence:
The suite runs nightly only; a broken merge is found up to 18 hours later.
Impact:
Bugs are found after the author has moved on, and fixes take longer.
Recommendation:
A 10-minute smoke set on every pull request that blocks the merge when it fails.

No visibility into performance before release Medium

Evidence:
Two of the last six incidents were slow search responses at peak hours.
Impact:
Slowdowns reach customers first.
Recommendation:
Apache JMeter tests for search and checkout with p95 limits, run weekly and before major releases.

4. 90-day roadmap

Days 1–30: stabilize

  • Per-test data through the API
  • Quarantine and fix the 20 flakiest tests
  • HTML reports with traces in CI

Days 31–60: shift down

  • API tests for payments and bookings
  • Smoke set gating every pull request
  • Start moving journeys to Playwright

Days 61–90: hand over

  • JMeter checks with latency limits
  • Retire replaced Selenium tests
  • Walkthroughs and pairing with the team
